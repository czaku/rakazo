This repo uses **two long-lived branches** with **machine-driven promotion**. The
model is two-trunk; the machinery that moves `main` is `runecode promote`.

## The two trunks

- **`develop`** — the integration trunk. All task branches merge here; staging
  deploys from here; keel daemon/docs commits land here.
- **`main`** — the release trunk. **Never committed to directly.** It moves
  **only** by `runecode promote`, which fast-forwards `develop → main` — the
  sole exception is an open **hotfix** landing (see below). A pre-push hook and
  `runecode doctor` enforce this.

No other long-lived branch exists — no `dev`, no `develop-*`, no second trunk.

## Task branches

- Named `task/<KEEL-ID>-slug`, cut from `develop`, one per keel task.
- For parallel lanes they live in `.worktrees/<task-id>`.
- Merged into `develop` with `--no-ff` at the MERGE stage.
- Deleted (local **and** remote) immediately after harvest.

## Promotion (`develop → main`)

`runecode promote`:

1. Asserts you are on `develop` with a clean working tree.
2. Runs the promotion gates: the project test suite (from
   `keel/execution.yaml`), `sentinel schema:validate` (if `sentinel.yaml`
   is present), and `runecode check` (must report no blocks).
3. Fast-forward-only merges `develop` into `main` (`git merge --ff-only`),
   publishes `main` with a plain push, and returns you to `develop`.

If any gate fails, or the fast-forward is impossible, it refuses (exit 1) and
prints the reason — it never rewrites remote history. Because the merge is
fast-forward-only, `main` never contains commits `develop` lacks — except an
open hotfix awaiting back-merge (see below).

**Cadence:** promote after each harvest (the MERGE stage invokes it); a nightly
fallback is allowed. `runecode doctor` **warns** at promote-age > 7 days and
**blocks** at > 14 days or when `main` is > 300 commits behind `develop`.

## Hotfix

- `hotfix/<KEEL-ID>` is cut from the released **tag**, merged to `main` (which
  tags a patch), **and** back-merged to `develop`.
- The pre-push hook **allows** this landing on `main` because every commit
  `main` gains is reachable from the open `hotfix/*` branch — no
  `RUNECODE_ALLOW_PUSH` override is needed for a proper hotfix. A push that
  carries a commit **not** on the hotfix branch is still blocked.
- `runecode doctor` verifies the back-merge returned `main..develop` to a
  fast-forwardable state (no commits stranded on `main`).

## Stabilization branches

- `release/<deployable>-<major.minor>` is allowed **only** around a store
  submission, for at most 14 days (doctor warns past that), deleted after the tag.

## Hygiene (doctor warns)

- Unaccounted `git worktree list` entries.
- Stray duplicate remotes.
