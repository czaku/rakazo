# Versioning & Releases — rakazo

> Generated by `runecode`. Do not hand-edit — run `runecode setup` /
> `runecode audit --fix` to regenerate. The header hash above detects drift.

Versions are **generated**, never hand-edited. The single source of truth is
`versions.json` at the repo root; `runecode version generate` writes the
platform-native fields from it.

## Source of truth — `versions.json`

Schema `runecode/versions.v1`:

```json
{
  "$schema": "runecode/versions.v1",
  "product": "rakazo",
  "train": "1.0",
  "deployables": {
    "api": { "path": "backend", "version": "1.3.2" }
  }
}
```

- **`train`** — the `MAJOR.MINOR` shared by `ios` + `android` (patch may
  diverge for a platform hotfix).
- **`version`** — strict SemVer `MAJOR.MINOR.PATCH`. `"1.0"` is a validation
  error.
- **`buildNumber`** — present only where a build counter exists (native apps),
  and always the literal `"derived"`. A numeric literal here is a validation
  error — that is the `0.1.2563`-class corruption this design kills.

## Generation, never hand-editing

`runecode version generate` writes:

| Deployable | File | Field |
|-----------|------|-------|
| `ios` | `apple/Configs/*.xcconfig` | `MARKETING_VERSION` |
| `android` | `google/app/build.gradle.kts` | `versionName` |
| `api` / `web-*` | `<path>/package.json` | `"version"` |

Every generated value is stamped with a `runecode-versions <hash>` marker.
`runecode version check` fails on drift (a generated field changed but
`versions.json` did not — i.e. a hand-edit).

## Build numbers are derived, never set

`CURRENT_PROJECT_VERSION` (iOS) and `versionCode` (Android) are computed at
build time as `git rev-list --count HEAD` — monotonic and unforgeable. They are
never stored in `versions.json` (marked `"derived"`).

## Semantics

- **Apps** (`ios`/`android`) use the **train** `MAJOR.MINOR`, shared across
  both platforms.
- **`api`** uses **strict SemVer**; a breaking contract change (sentinel
  contract drift) **requires a major bump**.

## Bumping

`runecode version bump <deployable> <major|minor|patch>` edits `versions.json`
and regenerates. A train bump moves `ios` + `android` together. Do this inside a
release keel task.

## Changelog

`runecode version changelog <deployable>` regenerates that deployable's
`CHANGELOG.md` section from the conventional commits between its tags.

## Releasing

`runecode version tag <deployable>` creates the annotated tag
`<deployable>/v<semver>` on `main` and rolls the changelog. **Every
store-released version must have a matching tag** — `runecode doctor` flags a
released manifest version with no tag.
